# Learnings register

One deduplicated, numbered register of everything already learned building and running this
pipeline. **Check this before designing anything.** Every entry cost real time, tokens, or risk
to discover once. The reason this file exists: a documented-three-times fact (the API cannot pin
comments) still got re-planned as "pin via Python script" in a later session, because the
learnings lived in scattered handoff docs no session auto-loaded. That must not happen again.

Sources merged: an earlier playlist-pipeline handoff doc (lessons L1-L16), the original pipeline
handoff doc (gotchas §10, safety rails §11, client-path notes §13), an issues-anticipated doc, a
troubleshooting doc, the SEO settled-decisions log, and an early 6-agent adversarial board review.

Column key: **id** · **lesson** · **source** · **phase it guards**

**A note on scope, so this reads honestly against the rest of the repo:** this register documents
the full development history of this pipeline's lineage — including a real flagship client
engagement run over several hundred videos across multiple modules — genericized for this public
repo. The `core/` code and README here are landing in stages (see the commit history); this
register is the accumulated doctrine behind that code, not a claim that every phase, gate, or
script it references is already live in this repo today. Where an entry names a phase (chapters,
push, comments, etc.) that hasn't landed here yet, treat it as the lesson that will shape that
phase when it does.

## A. Auth / OAuth

- **R1** macOS system Python blocks `pip3 install` (PEP 668, "externally-managed-environment"). Always use a venv; never suggest `--break-system-packages`. · L1 · Phase 0
- **R2** The venv must be re-activated in every new Terminal session (`source venv/bin/activate`). Symptom of forgetting: `ModuleNotFoundError`. · L2 · Phase 0
- **R54** No venv existed anywhere in this repo despite R1/R2 assuming one  -  global Python only had `yt-dlp`, none of `google-auth` / `google-auth-oauthlib` / `google-api-python-client`. Created `venv/` at the project root with exactly those 3 packages, the only third-party imports any current `core/` script uses. `pyproject.toml` + `requirements.lock` added at project root. Activate with `source venv/bin/activate` before any command. · an early repo audit · Phase 0
- **R3** `auth_setup.py` needs the `OAUTHLIB_INSECURE_TRANSPORT=1` prefix or the local OAuth flow errors. Baked into the run command, not typed by the operator. · L3, §10.9 · Phase 0
- **R4** OAuth authorization codes are single-use. If exchange fails or the code is mistyped, generate a fresh URL  -  never reuse. · L4 · Phase 0
- **R5** Pre-warn the channel owner about Google's scary consent wording ("can permanently delete your videos") and the unverified-app warning BEFORE sending the auth link. Include the revoke-anytime line (myaccount.google.com). · L5, §9 · Phase 0
- **R6** Token expiry: a valid refresh token auto-refreshes mid-run (the "Token was expired, refreshed silently" print is normal, not an error). A fully-expired token means re-run `auth_setup.py`, not a stack trace. Testing-mode tokens expire ~7 days  -  collides with multi-day runs; flip the OAuth app to In-production before a flagship client run. · L6, §10.8 · Phase 0, 8
- **R7** `token.json` authorizes actions as the signed-in account only. Each channel needs its own authorization; one channel's token never touches another's. · §9 · Phase 0
- **R8** The OAuth scope is `youtube.force-ssl`  -  the minimum scope that still allows metadata edit + comment insert. Google bundles delete-permission into it; there is no edit-but-not-delete scope. The honest safety claim is "the code never calls delete + snapshot gives revert + access is revocable," NOT "the token cannot delete." Never overclaim this in a pitch. · §9, §11, board · pitch/safety
- **R53** Google Cloud's "OAuth client created" confirmation modal shows the full client secret in plain text, not masked. Click **Download JSON** straight from that modal instead of screenshotting it. If a secret ever lands in chat or a screenshot anyway, don't try to redact after the fact  -  delete that OAuth client and recreate a fresh one. · an early repo audit · Phase 0

## B. API gotchas

- **R9** ⚠️ **The YouTube API cannot pin comments. It cannot even read pin status back.** Documented 3× and violated in planning once  -  this is the entry that justifies this whole register. Pinning is forever a human Studio click or browser automation, never a Python endpoint. Never promise API pinning to a client. · L10, §10.1, board · Phase 11
- **R10** `videos.update` silently wipes `defaultLanguage` and `defaultAudioLanguage` unless they are read and re-sent. `push.py` preserves them  -  keep it that way. · §10.3 · Phase 8
- **R11** Comment spam filter: identical comment text across many videos can trigger `processingFailure`, hold-for-review, or silent disappearance. Mitigation in place: 8-15s randomized pacing (held 13/13 and 15/15 in testing). At 384-video scale, add 3-5 approved text variants. · L11, §10.4, board · Phase 10
- **R12** A logged "posted" comment is NOT proof it is still visible  -  the spam filter can vanish it after the fact. Add a delayed liveness recount via `commentThreads.list` on logged comment_ids. · board · Phase 10, 12
- **R13** YouTube caps titles at 100 characters. `push.py` skips any video whose new title would exceed this and flags it for manual shortening. · §10.5 · Phase 8
- **R14** YouTube normalizes tags to alphabetical order on save. The set matters, the order does not  -  do not "fix" the reordering. · L8 · Phase 8, 12
- **R15** `defaultLanguage` can normalize from `en-IN` to `en` on save; audio language stays full (`en-US`). Expected, not a bug. · L9 · Phase 12
- **R16** `quotaExceeded` / `rateLimitExceeded` / `dailyLimitExceeded` must HALT the whole run cleanly with resume instructions  -  never be misclassified as a per-video failure that keeps hammering doomed calls. Idempotent logs make resume free. · board (critical) · Phase 8, 10
- **R17** More than ~60 hashtags in a description makes YouTube ignore ALL of them. Keep the count tiny (this pipeline uses exactly 5). · board/SEO · Phase 6, 7
- **R18** A hashtag placed in the TITLE suppresses the first-3 description hashtags from displaying above the title. Titles carry no `#`; the displayed trio must come from the description. · board/SEO · Phase 6, 7

## C. Script engineering

- **R19** Idempotency is by video_id: `push.py` and `post_comments.py` read their log CSVs at startup and skip completed IDs. Safe to stop/restart. Do NOT switch to position-based skipping. · §10.6 · Phase 8, 10
- **R20** Retry logic is exponential backoff at 2s/4s/8s with jitter, up to 3 attempts, for transient errors only (not quota  -  see R16). · §4, board · Phase 8, 10
- **R21** `datetime.utcnow()` is deprecated → use `datetime.now(timezone.utc)`. Patched in this repo; keep it patched. · §10.2 · all
- **R22** Terminal truncates long titles in dry-run output. Cross-check intended changes against `config.json` and the CSV logs, not the visual display. · L7 · Phase 5
- **R23** ⚠️ Wrong-channel guard: a stale symlinked `token.json` pointed at the wrong channel is the single worst incident possible. Every mutating script asserts the authorized token's channel ID == `config.expected_channel_id` before any write, and aborts on mismatch. · board (critical) · Phase 1-10
- **R24** Title rule is year-REPLACE, not blind-append. A naive append produced "MATH 2025 … | MATH 2026" on one live video. Logic: already-suffixed → skip; contains MATH 2024/2025 → replace; else → append. Cross-playlist overlap (88% on the channel) and re-runs make blind append recur at scale. · board · Phase 8
- **R25** For any script over ~50 lines, write it with a heredoc (`cat << 'PYEOF' … PYEOF`), never by pasting into nano (silent truncation). Verify with `wc -l` and `tail -5`. · §10.9 · Phase 0
- **R26** Mac sleep drops the API connection mid-run. Prefix long runs with `caffeinate` or keep the Mac awake. · §10.7 · Phase 8, 10
- **R27** After a push, Studio can take 30-60s to reflect changes; hard-refresh Cmd-Shift-R. Trust the log CSV (API-reported success) over the Studio display. · §10.10 · Phase 8, 12
- **R28** On macOS zsh, pasted URLs can appear invisible or arrive with a bracketed-paste `[200~` prefix; percent signs at the prompt are cosmetic. Paste once, trust it, press Enter  -  never paste twice. · §10.9 · Phase 0

## E. SEO  -  settled decisions (from the SEO decisions log; treat as decisions, not suggestions)

- **R40** Triple keyword match: the primary keyword appears verbatim and uninterrupted in (1) the title, (2) the first 200 characters of the description, and (3) Tag 1. All three exact string matches. · SEO decisions log · Phase 6, 7
- **R41** Tags 1-4 appear as verbatim, uninterrupted substrings within the first 200 characters of the description. Build the hook sentence AROUND the tag, not through it. · SEO decisions log · Phase 6, 7
- **R42** Year qualifiers ("MATH 2026") return near-zero YouTube search volume. Use in human-readable titles only (branding), never as the primary keyword anchor in descriptions or tags. YouTube infers exam cycle from upload date. · SEO decisions log · Phase 6, 7
- **R43** An umbrella exam-group name returns zero search volume → use the individual member exam names in titles instead of the umbrella term. · SEO decisions log · Phase 6
- **R44** One subject area's standard abbreviation has two valid letter-orderings, and they perform very differently as search terms: the audience-familiar ordering wins on thumbnails for brand recognition, while the higher-volume ordering should be pushed into tags and description text for reach, not the thumbnail. · SEO decisions log · Phase 5, 6
- **R45** For one recurring topic name, the two-word phrasing substantially outperforms the single merged word; British spelling ("analyse") outperforms American ("analyze") for this Indian audience. · SEO decisions log · Phase 6
- **R46** vidIQ MCP: country IN, includeRelated true, run 2+ seeds per session (one broad + one compound-specific, e.g. a subject-plus-topic phrase). Research is per-TOPIC-CLUSTER, not per-video (384 videos → ~20 clusters → ~40 calls, not 770). Cache and archive results per run  -  an unarchived keyword baseline is unrecoverable. On a credits error, proceed with calibrated knowledge and flag once. · SEO decisions log, board · Phase 5
- **R47** Enrollment URLs carry expiring session params (orderId, transactionId, promoCode). Always strip them and use the clean course-page URL; flag the action explicitly so the full string can be restored if preferred. · SEO decisions log · Phase 6, 10
- **R48** No em dashes anywhere. Bullets are 2-3 words, directional only (never action-verb benefit prose). Description delivered as one code block. Colon not dash in prose lists. · SEO decisions log · Phase 6, 7

## G. Environment / tooling (cross-project)

- **R68** A link in a YouTube description only becomes a CLICKABLE hyperlink if it is (a) an `https://` URL and (b) NOT immediately followed by punctuation. Seen live on an earlier pilot client's canary video: the hook ended with a Telegram link followed immediately by a full stop, and that trailing full stop got swallowed into the URL, so it rendered as dead text. Fix, baked into the pipeline for EVERY client: config link is `https://...`; `write_descriptions.sanitize_links()` upgrades bare -> https, strips any punctuation glued to the URL, and guarantees whitespace after it; `validate.py` V1 now checks clickability (https + no trailing punctuation) instead of "link in first 200", which also frees the 200-char budget for keywords. Applies to the comment link too. · pilot run, Phase 8 · Phase 8
- **R74a** The zero-delete invariant covers COMMENTS too, not just videos, and it is a CLIENT PROMISE, not merely a code property. The owner was told verbatim: "our tool only edits titles and descriptions, it has zero delete code." So after reverting a run, if someone asks to also remove the posted comments, do NOT write a comment-delete script (`comments().delete` / `setModerationStatus`): it would (a) break the repo's zero-`.delete()` invariant (R31), and (b) contradict the general "zero delete code" assurance given to the owner, even though comments are not videos. The honest safety claim (R8) is "the code never calls delete"  -  it dies the instant ANY delete call is added, for this client and every future one. Removing a posted comment is a MANUAL owner action in Studio (like pinning, R9); `post_comments.py`'s own reminder already says exactly this. The only `os.remove` in the repo is local temp-file cleanup (a stray `live_chat.json`), never a YouTube delete. Verified zero `.delete()` across `core/`. · pilot run reversal · Phase 10
- **R73** Phase 0a playlist audit (`audit_playlist.py`, zero quota, no auth) must run FIRST, before OAuth or config, for every client. On a 384-video, 117.6-hour flagship client run it instantly surfaced what would otherwise ambush the run: **133 titles (35%) exceed 100 chars once a year suffix is appended** (each needs a hand-written proposed_title, R62  -  that is the run's real workload, discovered on day zero, not at push); 9 stale prior-year markers + 1 older one (replace_years list), 4 already-suffixed current-year titles (idempotent skips); 0 foreign/private/deleted (clean scope, unlike an earlier pilot client, R61); quota day-plan ~3 days push + ~3 days comments at 9,000/day. The audit's keyword histogram (arithmetic/algebra/geometry/numbers/P&C/TSD...) is the Phase 3 module-map raw material. · flagship run, Phase 0a · Phase 0a
- **R74b** Scale fixes for 350+ videos and 1-2hr videos, shipped in one pass: (a) `build_chapters.py` count bands now follow the rulebook for long videos (<=30min: 4-6, <=75min: 6-10, else 7-12), the vtt window is ADAPTIVE (~120 windows regardless of length) and the cap is 30k chars, so a 2-hour video's chapters cover the whole timeline instead of the first ~25 min; end_buffer scales to 3 min on long videos. (b) `write_descriptions.py` samples head+middle+tail of long transcripts (a 1-2hr video is 60-100k chars; the old 15k head-truncation grounded descriptions in only the opening). (c) `classify_descriptions.py` is now idempotent + flushes after every video (a crash at 300/384 no longer redoes 300 Gemini calls). (d) `post_comments.py` rotates config.comment.variants across videos (384 identical comments = spam-filter bait; use 3-5 variants at scale). (e) Testing-mode token (7 days) vs a ~6-day quota plan is TIGHT: before a flagship run either publish the OAuth consent screen to Production (removes the 7-day refresh-token expiry; the unverified-app Advanced->Proceed flow stays the same) or book the owner for a mid-run re-auth. · flagship run prep · Phase 2, 6, 6b, 8, 10
- **R75** Context hygiene for long execution-copilot chats (the operator runs the pipeline through a chat that WILL exceed its context on a 384-video run): the chat is a VIEW, files are the MEMORY. RUN_STATE.md is the single source of truth; every phase boundary updates it; every new chat starts by reading it (plus CLAUDE.md + this register) and may NOT rely on chat scrollback. Hard-won points: (a) YouTube silently ignores the WHOLE list if the first stamp is not 0:00  -  two relabel videos on an earlier pilot client had first stamps at 0:32 and 1:20 (their chapters never displayed); force first to 0:00 even in relabel mode. - **R67** A single channel can mix spoken languages video-by-video, and whisper large-v3 recovers the ones YouTube mangles. - **R63** ⚠️ Exam-year naming differs by exam, and getting it wrong points a whole channel at a dead cohort. Some exams are named for the year they are HELD (so the name and the live cohort match). - **R62** (RESOLVED) `push.py` could not push a per-video title or per-video tags. It derives the title mechanically from the LIVE snippet via `build_new_title()`, and applies one uniform `config.tags` list to every video. The approved CSV carries only `proposed_description`.
